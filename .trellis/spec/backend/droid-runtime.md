# Factory Droid Runtime

## 1. Scope / Trigger

Apply when starting, resuming, indexing, or rendering a Factory Droid session.
Droid is a session-level runtime beside Pi. It is not a second agent framework
and it does not replace Pi extensions, model catalogs, or slash commands.

Local, WSL, and SSH share one implementation: `pilo-server` runs in the
connection environment and starts `droid` there. Do not copy a remote project
to the desktop. SSH connections that run Pi locally still run Droid on the
remote server. Droid has no SSH workspace extension.

## 2. Process

- Launch with `droid exec --output-format acp --auto medium --cwd <project>`. Stdin and stdout are newline-delimited ACP JSON-RPC 2.0. Do not send a Factory `factoryApiVersion` / `factoryProtocolVersion` envelope.
- When the connection's `droid_executable` is empty, resolve the program on the login PATH in this order: dk 1.1.0's `droid-dk` shim, then `dk run <droid>` when the shim is absent but both `dk` and `droid` exist, then the native `droid` CLI. The shim is the GUI entry (`dk run droid` plus the caller's arguments) and is used even when `droid` itself is not a file on PATH. `dk run` is what injects dk's managed `FACTORY_API_KEY`. Pilo does not read or store the key, and dk's `Using key` stderr banner is dropped before it is forwarded. A non-empty `droid_executable`, including the bare name `droid`, launches that program directly and skips dk. The shim receives the same `exec` arguments; the `dk run` fallback receives `run`, the native `droid` path, then those arguments.
- Handshake sends `initialize` with `protocolVersion: 1`, empty `clientCapabilities`, and `clientInfo.name: "pilo"`. Do not advertise filesystem or terminal capabilities. `droid` 0.230 answers with `protocolVersion: 1` and `loadSession: true`. Record the version the agent returns. Version 2 `session/set_config_option` calls also send `type: "id"`.
- A new session sends `session/new` with `cwd` and `mcpServers: []`. A Factory JSONL path resumes with `session/load`, the file stem as `sessionId`, the same `cwd`, and `mcpServers: []`. History replay notifications that arrive before `session/load` returns are discarded. The desktop transcript still comes from the Factory JSONL.
- When `session/new` or `session/load` returns an `autonomy_level` option whose choices include `medium` (droid 0.230) or `auto-medium` (droid 0.244) and whose current value is not that level, one `session/set_config_option` sets it. A failure leaves Droid's current autonomy in place. Do not call `authenticate`. A missing login is the agent's error text, surfaced as a runtime error. Pilo does not store `FACTORY_API_KEY`.
- User text is `session/prompt` with `sessionId` and one text block. The same call's result carries `stopReason` and ends the turn. `end_turn` settles. Any other stop reason becomes assistant text when the turn streamed nothing. A JSON-RPC error does the same with the error message, then settles.
- The session result's model `configOptions` entry stays on the Droid process. Its `id` is usually `model`. Grouped select options (`{ group, name, options }`, as in Zed and t3code) are flattened and repeated ids dropped. Options marked deprecated, or whose name contains `[Deprecated]`, are dropped. Each remaining option is a Pi model: `id` from `value`, `name` from `name`, `provider` `factory`. The current value is `currentValue`.
- The `thought_level` option (`reasoning_effort` in droid 0.244) holds the selected model's thinking choices. Values map to Pi levels by name; `none` and `off` both become `off`, and unknown values are dropped. The choices change with the model (glm-5.3-flash: low/high/max; claude-opus-5-5: low…max; claude-haiku-4-5: off…high; `auto`: none). Every `config_option_update` and every `configOptions` response refreshes both the model and these choices. `get_state` returns `thinkingLevel`, `get_available_thinking_levels` returns the mapped choices, and the current model carries `thinkingLevels`, `defaultThinkingLevel`, and `reasoning`. `set_thinking_level` writes `session/set_config_option` with Droid's spelling of the level and waits, like `set_model`; a level the model lacks is an error.
- `get_available_models` and `get_state.model` read that catalog. `set_model` writes `session/set_config_option` with `sessionId`, `configId`, and `value` only, and waits. A `config_option_update` notification, or `configOptions` on the response, carries the new id. Do not change autonomy in that request. Other non-prompt desktop RPCs stay local and are not written to Droid stdin.
- Live `session/update` notifications become Pi events. `agent_message_chunk` and a not-yet-streamed `agent_message` become assistant text. `agent_thought_chunk` becomes thinking. `tool_call` / `tool_call_update` become `tool_execution_start` and, on `completed` or `failed`, `tool_execution_end`. `user_message_chunk` is ignored because the prompt was already emitted. A v2 `state_update` of `idle` also settles. `session/load` replay is not forwarded.
- Live stdout is translated into the existing Pi RPC events (`message_start`, `message_update`, `tool_execution_*`, `agent_settled`) and emitted as `pi.rpc_json`.
- `session/request_permission` is answered with `outcome: cancelled` and surfaced as `pi.error`. Other client requests get JSON-RPC `-32601`. This version does not show a permission dialog.
- Stop is the shared process stop: stdin EOF, then kill. There is no separate interrupt method.
- Commands, compact, steer, and follow-up are answered locally and are not written to Droid stdin. Model and thinking reads, `set_model`, and `set_thinking_level` are the exception above; the desktop runtime forwards them to pilo-server.
- Model-catalog probes through `pi.start` stay Pi even if a caller passes `agent: droid`.
- A draft has no Droid process, so `droid.models` (`{ droidExecutable, thinking }`) reads the catalog like t3code's ACP probe: it launches Droid with the same resolution, sends `initialize` and `session/new`, returns `{ models, model }` from `configOptions`, then stops the process. It runs in the scratch cwd `<temp>/pilo-droid-catalog`, which no project watches, and removes that cwd's Factory session directory right away and again 3 seconds later, because Droid writes `<id>.jsonl` / `<id>.settings.json` after `session/new` returns. Timeout 30 s for the handshake. With `thinking: true` it also selects each model once in that throwaway session to read its thinking choices (about 0.2 s per model, about 20 s for 82 models; pipelining does not help) within a 40 s overall budget, under the WebUI's 45 s limit; models not reached get no levels. That session-level switch does not write `~/.factory/settings.json`. Desktop calls it through `project_droid_models { projectId, thinking }`; the WebUI through `GET /api/v1/models/droid?projectId=&thinking=true`.
- `environment.droid_probe` resolves like a session launch (dk shim, `dk run`, then native `droid`) and reports that program and its `--version`.

## 3. Identity and history

- The connection stores `default_agent` (default `pi`) and an optional `droid_executable`. Existing connections stay Pi. An empty `droid_executable` keeps the dk-then-native resolution above; saving a detected path opts out of it.
- Each session stores `sessions.agent`. The choice is fixed when the session is created.
- A Factory path (`~/.factory/sessions/<slug>/<id>.jsonl`) forces Droid even when an older index row still says Pi.
- The Factory directory name is the project path with one leading `/` removed, `:` deleted, and `/` or `\` replaced by `-`, prefixed with `-`. Verified on Windows with droid 0.244: `C:\Users\me\app` → `-C-Users-me-app`.
- History source of truth is that JSONL. Its sidecar `<id>.settings.json` supplies the history's `model` (`provider: factory`) and `thinkingLevel` (from `reasoningEffort`); `session.read` allows that one non-JSONL file name, only under the Factory sessions root, and `session.delete` still accepts JSONL only. The first record is `session_start` with `id` and `title`. Later records are `message` objects whose `message.content` holds `text`, `thinking`, `tool_use`, and `tool_result` parts. `visibility: "llm_only"` is hidden. `visibility: "user_only"` is assistant text. A failed `agent_turn_outcome` is assistant text only when that turn saved no assistant text. SQLite stores only the session index.
- Pilo does not store `FACTORY_API_KEY`. The target environment must already have Droid installed and logged in. A missing login is a runtime error.

## 4. UI

- Desktop landing and Remote WebUI share `AgentPicker` next to the draft project picker.
- Droid sessions show the shared model picker on the desktop chat composer, the new-chat landing, and the Remote WebUI. The picker receives no Pi project scope, so it lists the Droid catalog directly and does not open on the Pi "常用" tab. That tab without a scope renders the unresolved-scope message. In a session, opening the picker starts or resumes the Droid process so the live catalog can load. On the desktop landing page and a WebUI draft, the catalog comes from `droid.models` instead, so no empty session is created; choosing Droid starts that probe in the background. Slash commands, attachments, steer, follow-up, compact, fork, Next Prompt, and cache keep-alive stay hidden. The thinking picker is shown for Droid on all three surfaces. A model chosen on the landing page is applied once, before the first prompt, and a thinking level the user picked there is applied after it, because a model switch resets Droid's level. In a session, thinking changes are applied live, like the model. `src/lib/droid-models.ts` loads in two stages: the quick probe resolves first (current model's levels only), then a background `thinking: true` probe fills every model's levels and notifies `subscribeDroidModels` listeners. A catalog without levels keeps levels already known for the same model. The catalog is cached per connection in memory and `localStorage` (`pilo.droidModels.v1`); a stored catalog is shown at once and re-probed once per app run, concurrent loads share one probe, and the picker refresh forces a probe. WebUI drafts keep the model choice locally instead of starting the runtime.
- `/new` remains a Pilo command. Other slash text is sent as a normal message.
